# AGENTS.md

Guide for coding agents working on **Last Stand**, a browser 3D wave-survival ARPG (Three.js + TypeScript + Vite). `README.md` is the player/contributor overview; this file covers what applies across the game.

**Every directory has an AGENTS.md of its own**, with what is relevant there: what its code does, its gotchas, what each was measured against and how it went wrong before. Before changing code, read the AGENTS.md of each directory on the way down to it. A `CLAUDE.md` beside each one imports it, so Claude Code loads it as it reads a file there. What is learned about an area goes in its directory's AGENTS.md; this file keeps what applies across the game. Areas too long for their directory's AGENTS.md have notes in `docs/agents/` (the heroes' heads, gear, bow and legs, the village, what the hero sees, the sounds...; the lab's in `tools/lab/`), and that AGENTS.md says in a line when to read each. Keep every AGENTS.md under 60k characters, so it has room to grow (every agent's session loads this one whole and each on the way down to the file it reads, and Claude Code warns past 150k): when one passes that, move its largest area into the AGENTS.md of a subdirectory where its code sits, or into a note of its own, with that line in its place. A note too is kept under 60k.

## Commands

```bash
npm install
npm run dev          # Vite dev server, http://localhost:5173
npm run typecheck    # tsc --noEmit (strict)
npm run build        # typecheck + production build into dist/
npm run check:pages  # after build: every asset path must work under the Pages base path
npm run stalls       # the game in the installed Chrome, traced: the browser's own stalls (tools/stalls/README.md)
npm run icons -- sheet  # every class's skill icons side by side at a slot's size (check, add: tools/icons/README.md)
npm run music -- loops piece.wav  # where a piece can loop; make, seam: the game's tracks (tools/music/README.md)
npm run new -- foe spitter  # a new foe, boss, house, place, screen or lab command, from a sibling (tools/new/README.md)
npm run photos -- ground <id> <name>  # a Poly Haven ground into a map's two photos (tools/photos/README.md)
npm run fire-bake -- stir=4  # the fire's simulation alone, a sheet of its frames, in seconds (tools/lab/commands/fire.md)
```

The game has no test suite. Verify changes with `npm run build` and by playing the dev build in a browser.

- **Pictures and measures of the game go through the lab** (`tools/lab/AGENTS.md`: how to write one, a command a module of its own in `node/commands/`; `tools/lab/COMMANDS.md`: every command in a line, made by `npm run lab -- docs`, and each in full). **A task that runs the lab more than once keeps `npm run lab:serve` up** (a background task, started before its first lab command and stopped with `npm run lab -- stop` before wrap-up: `tools/lab/AGENTS.md`), which boots each command's page ahead of it; every command runs on a fresh boot and gives the same result every time; `--ab` runs it on `origin/main` too and says which lines and pictures differ; `npm run lab -- check --ab` runs every hero's checks of a change to how they move, side by side; `npm run lab -- live` keeps a page between steps for trying a pose or a look by hand (pictures in under a second, in any look: wireframe, faces, parts and where each is on screen, skeleton; a reference laid over). The lab's own code has unit tests: `npm run lab:test`.
- **Every harness is permanent.** Write a new measure in the lab (`tools/lab/examples/handSpeed.ts` shows its parts: the state it measures checked to have happened, a canary it must catch), never as a script with a boot and a clock of its own, and keep it: from its first use it is a lab command, or part of one that measures the same thing, never a probe left in `.tmp`. The probes and films these files name that aren't in the repo (the bow probe, `legdet`, the zigzag and aim probes, the DPS probe...) were such scripts: each is a measure to port into the lab the first time it's needed again, as the carry's and the range probe's were.
- **A slow game on a player's device is played back here**, at its frame rate there: `npm run lab -- trace <code>` reads the report it sent, and `npm run lab -- perf <skills> --device phone|phone-hot|laptop` plays it as that device (its screen, and its GPU played by this one drawing that screen at more pixels: `tools/lab/node/devices.mjs`, each factor set on the device's own reports). This PC's own frame rate says nothing: it's capped by the display, and the 4070 Ti is 6 to 25 times the devices players use. Never clock the GPU down to play one: other agents share it. What this GPU can't play (a phone's tiled GPU paying for cut-out and blended pixels) the device measures itself: the pause menu's Performance tab has Profile this spot, which times each part of the frame where the player stands and sends it as a trace (`src/perf/AGENTS.md`).
- A hero's face is measured against a reference picture with `npm run facelab` (`tools/facelab/README.md`; once: `npm run facelab -- --setup`). The tools and how their code is written: `tools/AGENTS.md`.

## Workflow

- **Every change goes through a PR** from a branch off `main`; never push to `main` directly. Each PR from this repository gets a live preview at `https://pr-N.ls.wellscoped.dev/`, built by Dokci itself from the PR's head on our own host (no GitHub Actions in the way: there were days they didn't run at all) and linked from the PR's "Dokci preview" check (`server/game-preview/AGENTS.md`); a fork's PR gets one too, built only once the maintainer has approved its GitHub Actions run on that exact commit, or as pushed when its author is one `.dokci/project.yaml`'s `trustedAuthors` names (each push waits for its own approval, the earlier approved commit's preview staying up meanwhile, and the build comes within about 30 seconds of the approval). `pr-checks.yml` runs the tests, typecheck and build with a read-only token and publishes nothing; fork runs need the maintainer's approval on every push (repo setting "all external contributors"). Merging to `main` deploys production (`deploy-pages.yml`).
- **A build to try that isn't a change is a Dokci commit build, never a PR**: an old commit, `main` as it stood at some date, a step of a bisect. `dokci previews build --project <id> --commit <full sha> --profile default` builds the game at that commit and serves it at `https://c-<first 12 hex digits>.ls.wellscoped.dev/` (`.dokci/AGENTS.md`: its expiry, its scope, tearing it down); the project's id is `dokci projects list`'s, and a short sha is refused (`commit_missing`). A PR is for a change to merge: a draft PR opened to get a preview of `main` as of the morning of 2026-11-07 (#472, closed) showed among the changes to review, with a diff that undid two days of merges (from the owner: "we dont do this, docki allows building bisect commits without a PR").
- **`main` is protected:** PRs only, merged with a merge commit (squash and rebase merges are disabled); a branch need not be up to date to merge, only free of conflicts. **PR branches must be linear:** `git rebase origin/main` to update, never merge `main` into a branch. The `branch-policy.yml` check fails any PR containing merge commits. Merged branches are deleted automatically.
- Pages is served from the `gh-pages` branch, production alone (the PR previews are our own service's). Don't switch Pages to "GitHub Actions only" and don't delete that branch.
- Keep PRs focused on one feature.
- **A feature adds files; it edits shared ones only through a line of its own** (over the 300 PRs merged up to #706, the files most PRs touched were the lab's command lists, `main.ts`, `index.html`, `net/session.ts`'s `PROTOCOL`, the quality table and the AGENTS.md files, and the conflicts on rebase were there). Content goes where it touches no other PR's lines:
  - a foe: `src/data/foes/<foe>.ts` (its stats, guide note and trophy; its id declared there) and `src/entities/foes/<foe>.ts` (its model, its `fx`, its way of fighting), found by the folder; a boss's in `src/entities/bosses/<boss>.ts` instead, loaded and warmed at its wave (`game/bossReady.ts`);
  - a sound of a foe's or a skill's own: `src/core/sounds/<name>.ts`, built of `core/audio.ts`'s voices;
  - a co-op message: registered from its feature's module (`onMessages`, `net/messages.ts`), and its protocol a line of its own in `net/protocol.ts`'s parts (never a number bumped by hand);
  - a house of the village: `src/data/houses/<id>.ts` (its cottage, room and objects; its id declared there) and `src/world/houses/<id>.ts` (its room's build, from the kit `world/rooms.ts`); a place of the village (an object out of doors): `src/data/places/<id>.ts`, and `src/world/places/<id>.ts` if it builds something of its own (`world/placeKit.ts`);
  - a screen (a window of the UI): a folder `src/ui/screens/<id>/` with its module, markup (`<id>.html`, any other `.html` there too) and styles (`_<id>.scss`), all found by the folder: the module registers itself (`screen`, `ui/screenKit.ts`), the markup goes in at `index.html`'s `<!-- screens -->` and the styles at `styles/index.scss`'s `// screens` (`vite.config.ts`);
  - `npm run new -- <kind> <id>` starts a foe, a boss, a house, a place, a screen or a lab command as a copy of a sibling's files, marked so the typecheck names each until it's rewritten (`tools/new/README.md`);
  - a dialog: registered from its module (`dialog`, `ui/dialogs.ts`); a kind of village object: what it does, registered by its owner (`villageUse`, `game/villageUses.ts`); a panel's markup: `src/ui/html/<id>.html`, named in `index.html` by a `<!-- part: id -->` line;
  - a quality setting: one block of `SETTINGS` in `data/quality.ts`;
  - a lab command: its own module (`tools/lab/AGENTS.md`);
  - what's learned about a feature: its directory's AGENTS.md, as a bullet of its own in its `## Notes by module` list, led by the module's name in backticks and in its alphabetical place (not at a section's end, where every PR appended and the AGENTS.md files were the most conflicted files of all: `src/ui/AGENTS.md` was edited by 131 PRs from Oct 10 to Nov 18), or a note of its own in `docs/agents/` once it's long.
- **Lists every PR adds to are kept sorted, and each entry is added in its alphabetical place**, never at the end: two PRs appending at one list's end touch the same lines and conflict, two in their places rarely do. A list marked `// sorted` (`<!-- sorted -->` before a Markdown one) is checked by `npm run check:sorted` in the PR checks.
- **Shared engine work lands first, once, in a PR of its own; content built on it follows.** A piece lifted out of a stack and merged with its own copy of the stack's base (#705 took the boss toolkit of #668) left every PR of the stack conflicting in 27 files.
- The PR checks say which shared files a PR touches (`scripts/hubs.mjs`, a warning in the run's summary, never a failure): a feature's PR that touches one should say why.
- **The relay server's deploy** (Dokci, `.dokci/AGENTS.md`) must keep its route on trusted TLS: never bypass certificate verification or add a public-relay fallback.
- **Don't waste compute: a check run over and over takes minutes, not half an hour.** It runs below normal priority, which the lab sees to itself (`tools/lab/AGENTS.md`): at normal priority its runs froze the owner's desktop for 10 to 20 s. The lab is run hundreds of times over a task, so a round's cost multiplies. Before running a suite again and again, ask what one round costs and what of it is wasted, and fix the tool first: profile it (`--profile`), keep what can't change (an A/B's other side is kept by its commit, `out/ab-cache`), run independent commands side by side (`npm run lab -- check --ab`: every hero's gait, stops and ranges, the ranger's feet and carry, in sessions of their own), skip what the measure never reads (films, pictures), and while iterating run only the scenarios a change can touch (`--scenarios`, `--classes`). Run one command at a time, both sides each time, the mage's cape (the heroes had capes then) stepped throughout and each gait scenario run again for a film, the same check took 31 to 35 minutes a round, and was run five times in a day.
- **This PC is shared: never load it for more than about two minutes unasked.** Several agents and the owner work on it at once, and a full check or suite pins its CPU and GPU at 100% for as long as it runs. Never run a slow suite whole just to have a "before" number: take the old timings from what is already there (a past run's `out/check/durations.json` and logs, another worktree's, a PR's), or time one narrow job on each side. Ask the owner before anything that will load the machine longer, say how long, and run it once. Stopping a background task stops less than it seems: under Git Bash, an `npm run lab` command stopped by its task runs on to its end with all its browsers (stop it with `npm run lab -- stop`, which stops every lab command running from the tree), so check that nothing of yours is left running. (A cold `check --ab` of the old harness, run for a before-and-after table, held the owner's CPU and GPU at 100% for over 17 minutes and was stopped unfinished; one stopped earlier had run on unseen after the owner asked for all work to stop.)
- **When the work stops being smooth, stop and fix how it's done.** Running into the same wall again is the sign: a probe rewritten for each task, a result that turns out to have measured nothing, a restart before every measure, a hand-made swap to compare with `main`, a constant edited and reloaded over and over. Take the time then to build the proper tool, harness or refactor, typed, reused and documented in `tools/`, instead of one more quick script that might work. This repo keeps a high quality bar, and its tools are held to it too: an iteration should take seconds and its results should be trustworthy. (On the bow's carry, seven one-off probes in `.tmp` each re-copied the boot, the fixed clock and the ray tests; two reported clean while measuring nothing, and one issue took hours. `tools/lab` replaces them.)
- **A pose is decided as a person would hold it, then looked at as the player sees it, and only then measured** (`src/entities/models/AGENTS.md`): clip measures check a natural pose; they never choose one.
- **Check every deletion two or three times before running it**, however sure it looks, and whoever asked for it: a folder of scratch, a tool's `out/`, a branch, a file. List what it holds, and for each thing in it ask where it came from, where else it exists and what needs it: search the repo and the session's history for paths into it, and keep whatever can't be made again (a picture or piece the owner saved there, a reference, an original an asset was made from). Then delete only what was checked, by name, and say what was kept and why. Scratch folders aren't all scratch: the owner saves files into `.tmp` to hand them over (what can go and what to keep: `tools/AGENTS.md`'s Cleaning up). (Cleaning 16 GB out of `.tmp`, the references the faces were tuned against, which the owner had saved there, went with it, and came back only from the session's logs.)
- **Text with a backslash or a quote goes through the Write tool, never a shell heredoc** (an edit script, a commit or PR body, an issue): a heredoc read by Git Bash on Windows halves backslashes and loses escaped quotes (`\'` came out as `'` and closed a string in an edit script, and `\n` became a newline), again and again. Write the script or the body to a file in `.tmp` with the Write tool and run or pass that file (`python .tmp/edit_x.py`, `--body-file`, `git commit -F`).
- **Pictures in a PR or an issue go up with the GitHub CLI's `--attach`** (gh 2.105 or later; `gh pr create|edit|comment` and `gh issue create|edit|comment`, [GitHub's docs](https://docs.github.com/en/github-cli/github-cli/attaching-files-with-github-cli)): write `![Before (main)](./before.png)` in the body file and pass `--attach ./before.png`, once a file, and the link is rewritten to the uploaded picture (a file the body doesn't name is added at its end; alt text for one is `'./x.png#alt text'`). Up to 50 files a command, each at most 10 MB: PNG, GIF, JPEG, SVG, and mp4, mov or webm for a clip. If some uploads fail the command still posts with the rest and exits non-zero: read its output, and only for what failed fall back to a `pr-pictures/<name>` orphan branch linked by raw URL. Never delete an old `pr-pictures/*` branch unasked: the PR bodies that link to it lose their pictures (#694's did).
- **A/B against `main` without losing work:** commit what you have first (a `wip:` commit, squashed or reworded before the PR), and only then swap files: `git checkout origin/main -- <files>` to measure main, `git checkout HEAD -- <files>` to come back, and `git status` clean after. Never run `git checkout <ref> -- <file>` (or `git restore`, `git reset --hard`) over uncommitted changes, and don't use `git stash` as the swap: with a clean tree it stashes nothing and both sides of the A/B measure the branch, and checking a file out before stashing it throws its changes away (both happened, and an afternoon's tuning was lost).
- **Prompt starts with `new issue:`** (fork workflow): run `scripts/issue.sh "title" "description"` with a title and description you write from the prompt, then do the work on the branch it creates. When done, run `scripts/commit.sh "PR title" "PR description"` instead of committing yourself, and reply with the PR link.

## Product rules

- **Core loop:** after *every* wave the player chooses Bank (keep all loot, leave) or Continue (harder wave, better loot). Dying loses all unbanked loot. Loot is **hidden until banked**: nothing drops on the floor, items go straight into the run's bag (`gainLoot` in `game/run.ts`), and the HUD shows only counts per rarity. The bank summary reveals the items one by one, the most valuable first, each in its place in the list. Don't show what an unbanked item is (name, base, stats) anywhere. Don't change this without being asked.
- **The village lobby is a beta the player opts into** (`VILLAGE` in `src/core/beta.ts`; from the owner: "we will release this under a beta flag, users who want to try it will toggle it"): one build holds both lobbies, and the page's load decides which, by the address's `?village=1|0` (kept in the cookie `last-stand-beta-village`) or the cookie. Off, the default, the game is as it was before the village: the lobby is its panels over the battleground, and nothing of the village is built, lit, warmed or compiled (no lamps in the lit shaders, no fog of what he can't see, no depth read, no village maps). The pause menu's Beta tab switches it and reloads; on, a notice says so as the game opens and offers the old lobby (`src/ui/beta.ts`). **Anything new of the village's goes behind `VILLAGE`**, and anything it changes in shared code keeps the other lobby's way beside it: check both with `npm run lab -- <command>` (the lab boots the village) and `--panels` (the lobby without it; `light --panels --ab` holds its frames to main's). A co-op room is in its host's lobby (`src/net/AGENTS.md`). Opting in and out, the notice and a room refusing the other lobby are checked end to end by `npm run lab -- beta` (and `--panels`), the tab's and the notice's fit on every screen by `lab ui --states pauseBeta,betaNotice`.
- **With the beta on, the lobby is a village** (`src/world/village.ts`, `src/game/village.ts`): every control is a place or an object the hero walks to and uses (E near it, a click or a tap on it from anywhere): the portals to the Crypt and the Thornwood, each beyond the palisade at the end of a way of its own, the stash's chest, the hall of heroes, the campfire (co-op), the chronicle (save slots), the notice board (how to play), the ghost by the training yard's gate, a Thornwood foe by day and a crypt foe by night (the training grounds: a battleground and a wave reached, its foes shades). I opens the inventory anywhere, M the village's map; skills are cast in the training yard alone. A first visit walks a short training round it before the portals open (skippable, with a warning at a portal). In co-op the party shares it, lit for the host's hour.
- **Choosing a hero:** the hero selection screen (`src/ui/heroSelect.ts`) shows every class's hero in 3D in a room of its own, the hall of heroes (`src/game/hall.ts`, `src/world/heroHall.ts`), shown in the village's place when the hall on its terrace is used: a long hall walked into, the other classes' heroes standing on its dais at the far end (`standHeroes`); a first visit opens on it, and the hall's dais (walked to and used: the hero whose plinth he stands nearest in focus) opens it again, as the panels' Change hero does without the village (`docs/agents/ui-loading.md`).
- **The lobby floor:** gear given up in the lobby is thrown on the floor, not deleted, and is picked up again until a run starts (`src/game/AGENTS.md`).
- **Everything is procedural.** No downloaded models, textures or audio: geometry, canvas textures, rigs/animation, VFX and WebAudio sfx are generated at runtime. Don't add binary assets. The exceptions are screenshots in `docs/`, the painted skill icons (`src/ui/skillArt/AGENTS.md`), the optional painted party portraits (`src/ui/portraits/AGENTS.md`), the music (`src/audio/music/AGENTS.md`) and the photos a map recipe takes its colours from (`src/core/photos/AGENTS.md`: small, tiling, the owner's or CC0).
- **Originality:** this is open source. Skill, item, enemy and class names must be original. No Grim Dawn (or other game) names, trademarks or assets.
- The game is class-agnostic by name ("Last Stand"). More classes are planned, so keep class-specific code in class data, models and skills, not in the shared systems.
- **The UI must fit any screen size, desktop and mobile.** Anything that overflows or overlaps at some viewport size is a bug. The UI is a share of the screen whatever the OS's scaling; check every change at the sizes `src/ui/AGENTS.md` lists (its scales, its layouts, `npm run lab -- ui --screens`).
- **Installable, offline (PWA):** a plain reload must show a new deploy. Players meet a new deploy under the previous one's worker: check a change to the worker, or to what the page asks of another host, with `npm run lab -- pwa`. The worker and its caches are `scripts/AGENTS.md`, the page's side `src/ui/AGENTS.md`.
- **Touch:** everything hover-only needs a touch path (`src/ui/AGENTS.md`).
- **The guide stays current:** any change that adds or changes an enemy, a boss, a skill, a weapon style, a staff school, an item base or a mechanic updates the in-game guide in the same PR (`src/ui/guide/AGENTS.md`). Its figures are read from the data as it opens; its words (`src/data/guide.ts`) are not, and a new foe fails the typecheck without them.

## Architecture

Each directory below has an AGENTS.md saying more.

| Path | Contents |
| --- | --- |
| `src/types.ts` | Shared types: data definitions (`SkillDef`, `ClassDef`, `EnemyDef`, `Item`...) and runtime (`Model`, `Effect`...) |
| `src/data/` | Pure tuning data typed against `types.ts`: classes & skills, enemies, biomes (roster, boss per biome), items/affixes, waves, `balance.ts` (camera, arena, run constants) |
| `src/combat/skills/` | Skill behaviours, registered in `index.ts` (`SKILL_IMPLS`) and referenced from class data by `impl` name. Instant: `cast()`. Channel: `start/tick/stop` with a typed state object. Use `Needs<'field'>` to require optional `SkillDef` tuning fields |
| `src/entities/models/` | Procedural models, registered in `index.ts` (`MODELS`: the heroes there, each foe's by its file in `entities/foes/`); `rig.ts` = shared humanoid skeleton + pose helpers |
| `src/game/run.ts` | Wave flow, scoring, loot rolls, bank / continue |
| `src/world/` | `arena.ts` builds every biome and the lobby's village at boot and switches between them (`village.ts`: its plan `villagePlan.ts`, its ways out `villageWays.ts`, its fountain `fountain.ts`, its grass `meadow.ts`); one builder per biome (`crypt.ts`, `forest.ts`), shared pieces in `props.ts` (the night and day skies too), the Thornwood's leaf-card foliage in `foliage.ts`, its trees grown by ez-tree in `ezTrees.ts` |
| `src/loot/` | Item generation (base names and excluded stats per class), save slots (`saveSlots.ts`), persistent profiles, one per class and save slot (`localStorage` `last-stand.profile.<classId>.v1`; the pre-class `last-stand.profile.v1` migrates to slot 1's mage), the lobby's class (cookie `last-stand-class`), skill loadout (cookie `last-stand-loadout-<classId>`; a class with gear-driven skills keeps one per weapon style, `last-stand-loadout-<classId>-<style>`). Slots 2 and 3 put `s2` / `s3` after the `last-stand` prefix of each name |
| `src/fx/` | CPU particle pools, a fixed pool of 8 point lights (`lights.ts`), transient effects (`effects.ts`) |
| `src/core/` | The engine's host renderer (three's) and what it hands the engine each frame (the frame's size, the grade's numbers), the views, input, audio, procedural textures & materials, game-time scheduler (`timers.ts`) |
| `src/engine/` | The Rust engine (Bulwark, WebGPU) that draws the game's scene, and the bridge that hands it the three.js scene each frame (`STATE.md`: what works, what's next) |
| `src/net/` | Co-op: who simulates what (`role.ts`), the links (`transport.ts`: our relay server, `server/relay`, or `?net=local`), rooms, lobby and each player's own state (`session.ts`), the host's reports of the fight (`sync.ts`) |
| `src/ui/` | DOM HUD, lobby/menus, the guide (`guide/`), tooltips, loadout editor, item icons (inline SVG), skill icons (`skillArt.ts`), attributes; the stylesheets (`styles/`, SCSS); the world's overlays, drawn by three on a canvas over the engine's frame (`overlay/`, placed by `floaters.ts`) |
| `src/state.ts` / `src/events.ts` | Typed global state `G` and a typed event bus |

**Adding a class:** a data file in `src/data/classes/` registered in its `index.ts`, a model in `entities/models/`, and skills in `combat/skills/`. Class data also sets the lobby accent, its place in the hall of heroes (`hall`: role, traits, the skill it shows off, its banner's colour), the loadout panel title, the cast-point light and item base names; give new bases an icon in `ui/itemIcons.ts` and the class an equipment silhouette (`#equip .doll[data-class]` in `index.html`). Classes share no progress: each has its own profile. Switching class in the lobby rebuilds the `Player`, and `game/warmup.ts` builds every class's model at boot with everything it can wear shown at once (a hidden mesh compiles nothing), so a class switch or equipping anything compiles nothing. A switch builds the new hero from scratch, all but his head: its geometry is made once per face, hair and detail (`once` in `models/head.ts`: the hair's cards were 60% of a build, which took 95 to 170 ms, now 30 to 70) and shared by every build after (`userData.shared`, which a model's dispose keeps: `disposeGeometries` in `rig.ts`). Time a switch in the lab's lobby (abandon the run its set-up starts) by the browser's own clock, `__labClock.realNow`.

**Adding a biome:** an entry in `data/biomes.ts` (enemy pool, boss, minimap), a builder in `world/` registered in `arena.ts`, and its enemies each a file in `data/foes/` and in `entities/foes/`, with models in `entities/models/`. It adds exactly 10 point lights (one at each of its four portals), two of them casting the still shadows, and keeps the dais and the gates where every biome has them (`src/world/AGENTS.md`).

Outside `src/`: `tools/` (the harnesses: the lab, the face harness, the icons, the music, the stalls), `server/relay` (the co-op relay), `server/game-preview` (each PR's preview, built by Dokci), `server/traces` (the performance traces slow games send), `server/saves` (cloud saves: accounts with passkeys, each site's save), `scripts/` (the build's and the workflow's), `public/` (served as it is), `docs/` (notes, research, screenshots), `.github/workflows` (PR checks, production) and `.dokci` (the relay's deploy and the PR previews).

## Across the game

- **The Rust engine alone draws the game** (`src/engine`, Bulwark; `src/engine/AGENTS.md`, `src/engine/STATE.md`): the game keeps its three.js scene and the engine is handed it each frame. WebGPU is required: where the browser has none, or the engine doesn't start, the loading screen says so, and there is no other renderer to fall back to or to compare with (three's WebGL path and three's WebGPU drawing of the scene were taken out; the address reads no `?renderer=`). The comparison is a commit: `--ab` in the lab. three's WebGPURenderer stays as the engine's host alone (the labels' and the outline's canvas over the engine's); the guide's portraits are drawn by a small WebGL renderer of their own (`src/ui/guide/AGENTS.md`). A note in these files about three's programs, its passes or its WebGL patches is history kept for what was measured, unless it says the engine does the same.
- **NaN means black lines or boxes on screen.** Bloom smears NaN/Inf pixels across the frame. Known causes: a shader's `smoothstep(a, b, x)` with `a >= b` (undefined in GLSL and in WGSL, so write `1.0 - smoothstep(b, a, x)`), and `atan(0, 0)`. The engine's post chain cleans the scene as it reads it (`scene_at` in Bulwark's `post.wgsl`) as a safety net; still fix the source.
- **Bright effects:** light adds up, so the final grade (`core/renderer.ts`) compresses it the way the eye does, and effects and their lights stay at full strength: don't dim single effects to fix a bright scene. Wrap a new effect material in `nearGlow()` (`core/materials.ts`), keep lights off the camera in first person, and nothing large may flash or pulse faster than about 1.5 times a second (3+ flashes a second is a photosensitivity hazard). How the grade adapts, how effects dim with distance and what first person changes are in `src/core/AGENTS.md`; measure an effect with `npm run lab -- cast <skill>`.
- **A kind's foes are batched by the engine, by their look** (`src/engine/AGENTS.md`): look-alike materials share one engine material, so a kind's bodies draw as a few instanced calls. The crowds of three's renderers (`entities/models/crowd.ts`) are off. A foe's look changes through its kit's uniforms (`kit.u`: dissolve, frost, char, hit, edge) and its materials' `emissiveIntensity`, which the engine's kit look reads (`engine/looks/kit.ts`); a material of its own on one foe takes it out of its kind's batch (`src/entities/models/AGENTS.md`).
- **Point lights:** use the pooled slots in `fx/lights.ts`. Never add ad-hoc `PointLight`s: the engine lights a frame by 32 point lights at most, the village's lamps among them, and leaves out any past that, counted as not drawn (`MAX_POINTS` in `engine/lights.ts`).
- **Pipelines are made at load, never mid-game.** The engine's scene pipelines are compiled aside by the page (`engine/pipelinesAside.ts`: a draw whose pipeline isn't ready yet is left out, so the thing shows a few frames late and nothing waits), and the loading screens wait for them. A warm-up (`warmUp` in `core/shaders.ts`) compiles and draws nothing of three's now: it hands the engine what it would draw (`AHEAD.prepare`) and waits for its pipelines. `game/warmup.ts` hands over one of every effect, drop and skill visual, the hero with all he can wear and the lobby's place before the lobby shows; the fight's (every enemy, the other biomes) under the loading screen too, and the other heroes' (and the hall of heroes' room) after it (`game/warm.ts`), or under their loading bar when Change hero, a save slot or a co-op pick needs them first. A lobby control that needs what the lobby didn't warm goes through `whenWarm`. A skill with its own materials must return sample meshes from its `warm()` hook, or its pipelines are first asked for at its first cast. A pipeline first asked for after the loading screens is counted (`PIPELINES.late`) and said among a perf report's boot notes: it must stay none during play. The perf overlay's `Shaders N (+M)` counts three's programs, of which the scene has none now. The engine's own rules: `src/engine/AGENTS.md`.
- **What the game makes is weighed as what it downloads is:** its whole download is about 3 MB, and a texture, a buffer or a store it makes as it runs counts as much: say each one's size on the GPU, in memory and kept across visits, against a budget its tool checks. The fire's loop was 23 MB on the GPU, 97% of it empty air, and passed two reviews unmeasured (the village's PR and its port to main); now it's 416 KB there and 987 KB kept (`npm run fire-bake` and `lab:test` fail over its budget, `docs/agents/fire.md`). Before keeping anything big, ask how much of it is ever seen: crop it to that, keep it compact, and put on the GPU only what's drawn now.
- **Keep loading in short chunks:** a window moved to another monitor shows black until the main thread can paint it, so boot work yields between steps (biomes, enemy warm-up) and the procedural PBR maps are made in workers (`core/pbr.ts` recipes, `PRELOAD` list, `core/pbr.worker.ts`; a map missing from `PRELOAD` is still made on the main thread on first use, just slower), as are the hands' sculpts (`preloadHands` in `entities/models/hands.ts`) and every hero's head (`preloadHeads` in `entities/models/head.ts`, `head.worker.ts`, kept across visits in `core/kept.ts`: made on the page, a return's other heroes built behind the lobby made theirs there, 200 to 270 ms a piece on the 4080). Measure with a `longtask` PerformanceObserver: nothing much over ~0.5s. Time a boot with `npm run stalls -- --scenario boot` (a first visit and a return, step by step; `--url this,ref:main` beside main), and what each program costs to compile with `npm run lab -- programs --cost`.
- **Settings switch live:** a quality preset changes only what needs no shader change (the pixel ratio, MSAA, the shadow map's size, which parts cast shadows, a uniform's steps). Keep new settings in that category, or they cause compile hitches when switched (`src/core/AGENTS.md`). A setting reaches the engine by hand: it isn't the engine's until `core/renderer.ts` hands it over and `npm run lab -- rustcheck` holds it (`src/engine/AGENTS.md`).
- **What follows the world is drawn by three on a canvas over the engine's, not on the page** (`src/ui/overlay/AGENTS.md`): a page element moved every frame repaints what lies round it, and in Chrome on Windows a repaint that needs a Skia program not yet built holds the game's canvas up for 1 to 4 s. Anything else on the page that must move every frame goes on a layer of its own (`will-change: transform`), and a looping animation moves only a layer's transform or opacity (a loop of a shadow, a gradient or a background paints every frame: the stash's glow dropped the lobby to 44 fps, #267; `src/ui/styles/AGENTS.md`).
- **Co-op** (`src/net/AGENTS.md`): every game moves and casts its own player, the host's simulates the fight, and each game judges its own hero's hits as its own screen shows them. Anything with gameplay effect goes through the checks in `net/role.ts` (`hitEnemy` needs `by` and deals damage only where `dealsDamage(by)`; `hurtPlayer` only on the local player; props wear down where `hurtsProps(by)`): skill code runs on every game for its visuals. An enemy attack goes through `fx()` in `enemyAI.ts`. Use `G.players` for anything that concerns every player and `G.player` for the local one alone, and add a part to `PROTOCOL` in `net/protocol.ts` when the messages change (a line of your own, sorted).
- **Asset paths:** Vite `base` is `./`. In `index.html` reference assets root-absolute (`/favicon.svg`) so Vite rewrites them; `check:pages` fails on paths that would break under a subpath.
- Three.js 0.187 (the game's scene, and the engine's host renderer): use `THREE.Timer` (not `Clock`), which logs a deprecation warning.
- **Dev hooks:** in dev builds, `window.__G` (game state) and `window.__dev.spawnEnemy` are exposed for scripted testing and screenshots (stripped from production). Spawn enemies well away from the player (near the arena edge) or the player dies before the shot.
- **Developer mode** (`src/dev/AGENTS.md`): **only in PR previews and dev builds, NEVER in production, and it must stay that way.** Two locks: a build flag only the preview's Docker build sets (production's bundle has none of its code), and the preview's host. Never set `BUILD_PREVIEW` in production's build, nor load `src/dev` any other way. What it gives: F8 a panel (any wave and biome, foes, every piece of gear, god mode, the class, the frame's parts taken out live), F9 a free camera with the game frozen, F7 freeze.

## Style

- TypeScript strict. Keep data (`src/data`) separate from behaviour, and type new data against `types.ts`.
- Match surrounding code: short header comment per file, sparse comments explaining *why*, compact one-line helpers where the file already uses them.
- **Tools (`tools/`) are written to be read**, held to a higher bar than the game, as a harness is how the game's quality is judged (`tools/AGENTS.md`).
- Styles are SCSS in `src/ui/styles/`, on its theme and mixins (`src/ui/styles/AGENTS.md`). Honour `prefers-reduced-motion` for decorative animation.
