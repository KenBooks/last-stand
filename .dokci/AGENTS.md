# `.dokci`

Dokci's project (`project.yaml`): it deploys the co-op relay (`server/relay`) and the traces service (`server/traces`, under `/traces`), both at the relay's host, on every push to `main`, and each open PR's preview at a host of its own (`previews`, [`server/game-preview`](../server/game-preview/AGENTS.md)); production itself is on GitHub Pages (`.github/AGENTS.md`).

The rules across the game are the [root AGENTS.md](../AGENTS.md).

## Gotchas

- **Dokci relay TLS:** the production route in `.dokci/project.yaml` must explicitly set `entryPoint: websecure` and `certificateResolver: letsencrypt`. Omitting them creates an HTTP-only route even though the installed proxy redirects public HTTP to HTTPS; container health alone does not prove public TLS works. Keep the relay's internal HTTP port and health check unchanged, and verify trusted HTTPS at `/health` plus a WSS connection after the merged revision deploys. Never bypass certificate verification or add a public-relay fallback.
- **A new `configuration` value reaches the containers only with a deploy that's planned after it's bound.** On 2026-11-06 `LS_PREVIEWS_TOKEN` (the PR previews' old upload service's) was bound at 18:31; the redeploy started by hand from Dokci's page (#77) carried the configuration revision of the deploy before it, sat `queued` without ever running (a deploy here runs within a second of queueing and is healthy in 15 to 30 s), and once cancelled, each Redeploy failed in its "recovery phase" with no activity entry and no log. A push to `main` plans a fresh deploy (how #76 went out). Read what Dokci did with the owner's CLI (read scopes): `dokci activity list --limit 20` (each deploy's requested, queued, running, healthy) and `dokci environments show --project <id> --environment <id> --json` (each deploy's state and `configurationRevision`); `dokci projects list --json` gives the ids. A configuration change asks the owner to approve its plan in Dokci, whatever `requireManualApproval` says.
- **A Redeploy of a failed or cancelled deploy of the same commit never runs; push a new commit to `main` instead.** Dokci keeps one GitHub check ("Dokci deployment") per commit and configuration, and a deploy runs only while that check is queued. Once a deploy of the commit failed or was cancelled the check is completed, GitHub won't reopen it, and the replacement sits `queued` forever ("waiting for required deployment checks", with nothing in its log). That is what held #77 and, on 2026-11-06, #84 (the retry of #83). A merge to `main` makes a new commit with a check of its own (how #76 went out). Dokci (since `6e95400`, ADR 0069) now retires containers of services removed from the Compose files by itself (the PR previews' old `previews` service had kept production stuck in `reconciliation_required`) and replans a deploy whose configuration changed after its plan, rather than failing with "The recomputed Compose plan does not match the approved digest".
- **Every link Dokci shows must work** (Dokci ADR 0073, since Dokci `d53b054`): a route's `link` says how Dokci links it. The relay answers only `/health` and its WebSocket, so its route has `link: { hidden: true }`; the traces route has `link: { signInWith: LS_TRACES_TOKEN }`, so Dokci opens the traces page through a one-time link signed with that value (the format the page checks is in `server/traces/AGENTS.md`). Dokci also leaves out any link that answers an HTTP error. An older Dokci's agent refuses a manifest with `link` (it reads routes strictly), so a new route setting goes out only after the Dokci that knows it.
- **The policy is read from the PR's base commit**, so a PR opened before a change to `previews` (such as `feedback.comment`) gets it only once rebased onto the `main` that has it.
- **The traces service** has a route of its own on the relay's host (`pathPrefix: /traces`, the same entry point and resolver) and a volume (`traces-data`). Its read token is the project's `configuration` `LS_TRACES_TOKEN`, set in Dokci by the owner, never in the repo: unset, traces are still taken and kept, and nothing can read them. `LS_TRACES_TRUSTED` (comma-separated addresses, the owner's, also set in Dokci) is never held to the reports a day (`TRUSTED_ADDRESSES`). After it deploys, check `https://ls.wellscoped.dev/traces/health` and that the relay's `/health` and a WSS room still answer.
- **The PR previews** (`previews`, one policy, `pr`, for PRs into `main`): Dokci builds each open PR from this repository, drafts too (Dokci's ADR 0086), by a collaborator, and each fork's PR whose head commit's GitHub Actions run the maintainer approved, from its head (`server/game-preview/compose.yaml`) and serves it at `pr-{{ pullRequest.number }}.ls.wellscoped.dev` on `websecure` with `letsencrypt`, served the server's wildcard `*.ls.wellscoped.dev` certificate (Dokci's ADR 0082: Traefik issues none for a host a stored certificate covers; a host of its own over HTTP-01 only if the wildcard is missing), and links it from the PR's "Dokci preview" check once healthy and its host resolves. It reads the policy from `main` alone, so a change to it is tried only once merged. What a preview may hold is fixed by Dokci's schema (`G:\Git\dokops`, `GitHubProjectPolicyReader.Previews.cs`): `trust` must have `requireRepositoryCollaborator: true` (`allowForks: true` builds forks after approval, Dokci's ADR 0079; `trustedAuthors` lists GitHub logins whose forks are built as pushed, without it, Dokci's ADR 0085: KenBooks, akshvic), `cleanup.deleteVolumes` true, every resource set, no secrets or `configuration`, and only `DOKCI_SOURCE_SHA` is given to the build (no PR number). The DNS is the owner's: a wildcard `*.ls.wellscoped.dev` A record at the server, and its address in `DOKCI_PUBLIC_PROXY_ADDRESSES`. Check one with `dokci previews list`.
- **A commit build** (Dokci ADR 0087): the game at any commit of this repository, without a PR, for bisecting or trying an old build: `dokci previews build --project <id> --branch <name>` (its head now) or `--commit <sha>` (reachable from `--branch`, else `main`; a fork's commit is refused), `--ttl <hours>` 24 by default, 720 (30 days) at most, `--profile default`. It needs a key with the `previews:build` scope, which the owner gives. It is built like a PR's preview (the same policy, read from `main`, and stack) and served at `commitHostTemplate`, `https://c-<first 12 hex digits>.ls.wellscoped.dev/`, whose pages the relay and the traces take (`c-*` in their `ORIGINS`); it posts no check or comment, shows on Dokci's Previews page with its expiry, and is torn down when it expires, or earlier with the page's Clean up or `dokci previews teardown-prepare` and `confirm`. The same commit asked for again is the same build (its expiry pushed further).
- **Each preview build comments on its PR** (`feedback.comment: true`, Dokci ADR 0068, since Dokci `cadd3fb`): a new comment per push, and once it is posted the earlier ones are deleted (Dokci ADR 0074, since Dokci `4d626b5`: only Dokci's own comments for that preview, best effort), so a PR shows one, the newest, with the link, the short commit, the time from the push to ready and the build time (or, when it failed, the reason and the check's link). It needs the Dokci App's Pull requests: Read and write, granted 2026-11-06; without it nothing fails, and the "Dokci preview" check says the comment wasn't posted and repeats the link. Like the rest of the policy it's read from `main`, so turning it off is a merged PR too. The comment code is Dokci's (`GitHubPreviewComment*` in `G:\Git\dokops`, whose AGENTS.md maps it).
- **A Dokci bug found from here** may be fixed, since this repo is deployed by Dokci (repos without a `.dokci/` folder never touch it). First check whether a session has worked on Dokci recently and hand the bug to it (what you saw, the exact command and error, what you need back): it has the context. Fix it yourself in `G:\Git\dokops` only when there is none, following that repo's AGENTS.md (it commits straight to its `main` and deploys as a patch). The `dokci` CLI on the owner's PC needs `--profile default` on every remote command.
