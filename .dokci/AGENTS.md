# `.dokci`

Dokci's project (`project.yaml`): it deploys the co-op relay (`server/relay`), the PR previews service (`server/previews`, under `/pr-preview`) and the traces service (`server/traces`, under `/traces`), both routed at the relay's host, on every push to `main`; the game itself is on GitHub Pages (`.github/AGENTS.md`).

The rules across the game are the [root AGENTS.md](../AGENTS.md).

## Gotchas

- **Dokci relay TLS:** the production route in `.dokci/project.yaml` must explicitly set `entryPoint: websecure` and `certificateResolver: letsencrypt`. Omitting them creates an HTTP-only route even though the installed proxy redirects public HTTP to HTTPS; container health alone does not prove public TLS works. Keep the relay's internal HTTP port and health check unchanged, and verify trusted HTTPS at `/health` plus a WSS connection after the merged revision deploys. Never bypass certificate verification or add a public-relay fallback.
- **The previews service** has a route of its own on the relay's host (`pathPrefix: /pr-preview`, the same entry point and resolver) and a volume (`previews-data`). Its write token is the project's `configuration` `LS_PREVIEWS_TOKEN`, set in Dokci by the owner, never in the repo, and the same value as the repo's `pr-preview` environment's `PREVIEWS_TOKEN` secret: unset, what's kept is still served and every publish fails. After it deploys, check `https://ls.wellscoped.dev/pr-preview/health`, that the relay's `/health` and a WSS room still answer, and a publish run (`gh workflow run pr-preview.yml`).
- **A new `configuration` value reaches the containers only with a deploy that's planned after it's bound.** On 2026-11-06 `LS_PREVIEWS_TOKEN` was bound at 18:31; the redeploy started by hand from Dokci's page (#77) carried the configuration revision of the deploy before it, sat `queued` without ever running (a deploy here runs within a second of queueing and is healthy in 15 to 30 s), and once cancelled, each Redeploy failed in its "recovery phase" with no activity entry and no log. A push to `main` plans a fresh deploy (how #76 went out). Read what Dokci did with the owner's CLI (read scopes): `dokci activity list --limit 20` (each deploy's requested, queued, running, healthy) and `dokci environments show --project <id> --environment <id> --json` (each deploy's state and `configurationRevision`); `dokci projects list --json` gives the ids. A configuration change asks the owner to approve its plan in Dokci, whatever `requireManualApproval` says.
- **The traces service** has a route of its own on the relay's host (`pathPrefix: /traces`, the same entry point and resolver) and a volume (`traces-data`). Its read token is the project's `configuration` `LS_TRACES_TOKEN`, set in Dokci by the owner, never in the repo: unset, traces are still taken and kept, and nothing can read them. After it deploys, check `https://ls.wellscoped.dev/traces/health` and that the relay's `/health` and a WSS room still answer.
