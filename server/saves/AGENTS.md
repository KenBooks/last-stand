# `server/saves`

The saves service (`saves.mjs`; `serve.mjs` starts it): cloud saves (#382, milestone "Cloud saves"). A player signs in with a passkey, and each site's save is kept for every device. Deployed by Dokci beside the co-op relay and the traces, from the relay's `compose.yaml`, on the same host under `/saves` (`.dokci/AGENTS.md`). The game's side is #504; Google sign-in and the backups are #503.

The rules across the game are the [root AGENTS.md](../../AGENTS.md).

- `saves.mjs`: the HTTP side, every route in its header comment, and the settings (`settingsFrom`). `store.mjs`: the files it keeps. `passkeys.mjs`: WebAuthn through `@simplewebauthn/server`. `cleanup.mjs`: the daily cleanup. `google.mjs`: signing in with Google by redirect. `backups.mjs`: the nightly backups to Drive; `restore.mjs` writes one back; `driveToken.mjs` makes the owner's Drive refresh token, on the owner's PC.
- Tests: `npm run saves:test` (once: `npm ci --prefix server/saves --ignore-scripts`; the PR build runs both). They go through the library's real checks: `test/authenticator.mjs` answers as a browser's passkey does (an ES256 key, "none" attestation, CBOR by hand). `test/google.test.mjs` runs Google's sign-in and the backups against `test/fakeGoogle.mjs`, a stand-in for Google's token endpoint and Drive; each of its checks was shown to fail with what it guards switched off (the landing code's origin, its tab, its shape, linking from a preview, a link finished by another account, a preview's passkey counted as a way in, the upload's MD5, the return path).
- Run it locally: `DATA=.tmp/saves PORT=8789 ORIGINS=http://localhost:5173 node server/saves/serve.mjs` (`localhost` is a relying party by default).

## How it works

- **Accounts are ours:** a random id, with ways in attached: passkeys, and Google as another way into the same account. No name or picture is kept; a Google session keeps the verified email last confirmed at sign-in, privately returned only for that session; a passkey's user name is `Last Stand <first 6 letters of the id>`. An account with a production way in keeps at least one: the last passkey of production's relying party can't be deleted, nor production's Google unlinked, while it's the only one (`waysIn`). A preview-only Google account can have no production way in by design. A preview's passkeys don't count: production's login refuses them, and a preview's codes open previews alone (the security review of #516 found an account unlinking Google with only a preview's passkey left, locked out of production).
- **Sessions** are random tokens, given to the page once (it sends `Authorization: Bearer`, not a cookie: the game's pages are another site, and their browsers block third-party cookies). Only their SHA-256 is kept. A session belongs to the site it was made on and is refused from any other. It lasts `SESSION_DAYS` (180) since it was last used (checked on every request, and dropped by the cleanup), and its use is written down at most once a day.
- **Production is the one trusted site.** A PR preview or commit build runs unmerged code, which can send its token anywhere and replay it with any `Origin`. So a session of theirs reaches its own site's save and nothing past it: deleting the account and deleting passkeys answer 403 unless the session is production's, and a sign-in code it makes signs in on previews and commit builds alone (`previewsOnly`: the owner's choice, so a second device can join a preview before production has the game's side; at worst a stolen preview token reaches the account's preview saves, never production's, as a passkey made on a preview has `ls.wellscoped.dev`'s relying party, which production's login refuses). It may add a passkey only in its first 10 minutes, and only if a sign-in code made it (the player adding that site's passkey). The security review of #506 found each of these open; the test "a preview's token reaches nothing past its own save" checks them.
- **A site is a page's origin:** its host, `www.` left off, `:` as `_` (`last-stand.cc`, `pr-512.ls.wellscoped.dev`, `c-<sha12>.ls.wellscoped.dev`). A save is filed under the site the browser's `Origin` names, never one the page asks for. So a preview's code can never write production's heroes, and can read them only through `copy-production`, the player's own choice.
- **Passkeys' relying parties** (`RP_IDS`): `last-stand.cc` for production, `ls.wellscoped.dev` for every PR preview and commit build (one passkey there works on all of them), `localhost` for development. A passkey works only where its relying party fits, so a production passkey can't sign in on a preview. **The sign-in code** bridges them. Signed in, `POST /saves/link-code` gives 8 letters (production's sign in anywhere, a preview's on previews alone), good once for 10 minutes, one an account at a time (a new one replaces the last). Typed on another site (or device), `POST /saves/link` signs that page in to the same account, which can then add a passkey of its own there. Codes live in memory: a restart drops them.
- **The origins** (`ORIGINS`) are the game's pages alone: production, `pr-*` and `c-*`. They exclude `localhost` (any local app is) and the github.io address the game moved from (every Pages site of that user is), which the relay and the traces still take. Set `ORIGINS` to try it locally.
- **A save is parts** (`hero.mage`, `shared`...: the game names them, `^[a-z][a-z0-9.-]{0,31}$`, `PARTS_MAX` 16), each gzipped JSON of an object. Each part has a version, the device that wrote it and when. A write sends `x-save-base`, the version it builds on (0: new). A stale one is refused with a 409 and the version, device and time kept, so the game can ask its player which copy to keep (per hero: #382). The service never merges and never picks.
- **What it checks of a save:** its size and shape alone (gzip of a JSON object, unpacking to 512 KB at most). Saves stay the player's own and client-authoritative: cheating is out of scope (#382).
- **Copying production into a preview** gives each copied part a version past the preview's own. A device holding the preview's older copy is then told it changed (409), and never writes over the copy unseen. Production is never written from another site.

## Google

- **Identity display (#539):** `/saves/account` and sign-in responses return the current session's `via` and, for a Google session alone, its verified email. Email is display text, never an account key: Google bindings still use site + sub. Older Google sessions may lack email; sign in again to populate it. Passkey/code sessions reveal no other session's email. Never log email or put it in public health/traces. `google.test.mjs` checks these boundaries and reload from disk.

- **Sign-in by redirect** (`google.mjs`): the page asks `POST /saves/auth/google { purpose, returnPath }` and is sent to Google with the OAuth code flow: the `openid email` scopes, PKCE (S256), `prompt=select_account`, and a `state` remembered here (10 minutes, good once) with the page's origin (one of `ORIGINS`) and the path to return to (the page's own path and query, printable ASCII, never `//host`: a control or wider character can't go in a Location header). At most 10,000 are out at once. Google sends the player to `/saves/auth/google/callback`, the one route that takes no `Origin` (a navigation carries none); it trades the code at Google's token endpoint with the verifier and the client's secret, checks the id token's issuer, audience and expiry (straight from Google over TLS, so its signature needn't be checked: OpenID Connect Core 3.1.3.7), and sends the page home to that origin and path alone with `#cloud-google=<code>` (a one-time code, 2 minutes, holding what the sign-in is for and Google's id) or `#cloud-google-error=<why>`. Nothing is made or linked at the callback: whoever opens an address Google gave lands there. It all happens at `POST /saves/auth/google/finish`, from that origin alone, with the nonce the tab that began it sent and kept in its session storage. A code someone finished themselves and sent in a link would otherwise sign the receiver's game in to the sender's account, and is refused. An unknown or used `state` gets a 400 and no redirect: there is nowhere safe to send it.
- **Google is bound per site:** only Google's `sub` and the game's site are kept (`account.googles[site] = { sub, linked }`), indexed together in `store.mjs`. The same Google identity on production and on two previews can name three separate Last Stand accounts. A sign-in code may separately bring one account onto another site without changing its Google binding there. A new Google sign-in on a site makes an account if that site's `sub` has none (counted against `ACCOUNTS_PER_DAY`). Old `account.google` is migrated on load using its first Google session's site; if that session aged out, it defaults to production, so a preview-only account's old binding is not confidently identifiable.
- **Linking** (`purpose: 'link'`) needs a session, and production's: a preview's token may be anyone's, and Google linked from one would let its holder into production. It is finished with that same account's production session as well as the tab's nonce: linked at the callback (as first written), a link address sent to another player linked the receiver's Google to the sender's account, so the receiver's every Google sign-in landed in the sender's account (the security review of #516). A production `sub` on another production account offers a move only if that account has no production save or also has a production passkey. A preview's `sub` does not reserve production's. Unlinking (`DELETE /saves/google`) is production's alone too. A Google sign-in's session is `via: 'google'`; it may not add a passkey off production (only a code's may, in its first 10 minutes).
- **Moving Google:** the OAuth-proven link returns a one-use random offer if the identity is already bound elsewhere. The offer lasts 5 minutes and is bound to the target production session, account, site and Google `sub`. `POST /saves/google/move` checks those again, serializes with Google sign-in and both account writes, and moves only the production binding. The old account and all saves remain; a production save on it requires another production way in before moving Google. If a process stops between the two writes, the target's newer binding wins at the next load. The dialog warns when old preview saves may no longer be accessible.
- A production session issues a one-use copy code with `POST /saves/copy-code`; a separately signed-in preview account redeems it at `POST /saves/copy-production`. The code grants a copy of production's save into that preview alone, never a production session. A preview session alone cannot read the production save. The code expires after 10 minutes and is held only in memory.
- One site's Google sign-ins wait their turn (`withAccount('google <site> <sub>')`), so two at once make one account there.

## Backups

- **Nightly to the owner's Google Drive** (`backups.mjs`), as TimeInvoices keeps its own (`G:\Git\TimeInvoices\BACKUP.md`): every account and save as one gzipped JSON snapshot (`{ version, made, files: { 'accounts/<id>.json': text, 'saves/<id>/<site>.json': text } }`), uploaded into `Last Stand backups/` (`DRIVE_FOLDER`) under the `drive.file` scope (Drive shows the app only what it made), its MD5 as Drive reports it checked against ours, and those older than `BACKUP_KEEP_DAYS` (14) deleted. The Drive listing follows every page so retention still works after 200 backups. A run 5 minutes after a start (`BACKUP_FIRST_MS`) and every 24 hours (`BACKUP_EVERY_MS`); one finding a backup in Drive younger than 20 hours (`BACKUP_MIN_AGE_MS`) skips, so a deploy's restart doesn't upload another.
- `/saves/health`'s `backups` says `off`, `pending` (none since the start), `ok` with when the last one was made, or `failing`. The error itself is in the service's log (`backup`), not the health, which anyone can read. The likeliest failure is Google's `invalid_grant`: the OAuth app left in Testing, whose Drive refresh tokens last 7 days (TimeInvoices' BACKUP.md, "Google Drive disconnects every week").
- Handle an allowed page's OPTIONS request before `/saves/health`'s public GET response. A signed-in browser may preflight the health request when it sends Authorization; returning the health JSON without `access-control-allow-headers` hides the game's Google controls even though the endpoint itself reports `google: true`.
- **Restoring:** download the snapshot from Drive, stop the service, and `npm run saves:restore -- <snapshot.json.gz> <data folder>` (the `saves-data` volume's folder). It refuses a folder holding accounts unless `--replace`, which validates every path and value before emptying `accounts/` and `saves/`, and writes only paths of those two shapes. Start the service again: it reads the accounts at its start.

## Setting up Google (the owner, once)

1. **Google Cloud console**, a project for Last Stand: Google Auth Platform, **Clients**, a Web application client. Its authorized redirect URIs: `https://ls.wellscoped.dev/saves/auth/google/callback` (the sign-in) and `http://localhost:8791/` (the Drive token, step 5). No JavaScript origins are needed: no Google script runs in the game.
2. **Branding:** the app's name, `https://last-stand.cc` as its home page, `https://last-stand.cc/privacy.html` as its privacy policy, `last-stand.cc` and `wellscoped.dev` as authorized domains.
3. **Data access:** the scopes `openid`, `email` and `https://www.googleapis.com/auth/drive.file`. **Enable the Google Drive API** in the project's APIs.
4. **Audience:** External, publishing status **In production** (in Testing the Drive refresh token expires after 7 days and the backups stop).
5. **The Drive token:** on the owner's PC, with the client's id and secret in the environment, `npm run saves:drive-token`, open the address it prints signed in as the Google account the backups go to, and agree: it prints the refresh token.
6. **Dokci** (the relay's environment, `.dokci/AGENTS.md`): `LS_GOOGLE_CLIENT_ID`, `LS_GOOGLE_CLIENT_SECRET`, `LS_DRIVE_REFRESH_TOKEN`, then a deploy (a push to `main`). `https://ls.wellscoped.dev/saves/health` says `google: true` and `backups: { state: 'pending' }`, `ok` 5 minutes later; the backup is in `Last Stand backups/` in Drive.

## Limits

- `SAVE_MAX` (16 KB) a site's save, gzipped. That is about 2 times a full save (3 heroes, 60-item stashes: estimated at 6 to 9 KB, to be measured by #505's check). An oversized body gets a 413, never a cut connection.
- Writes per account and site, spread evenly: `WRITES_PER_HOUR` (300), `WRITES_PER_10_MIN` (50) and `WRITES_PER_MINUTE` (10), each in any such window (from the owner: "300 saves per hour... but not more than 50 in 10min, so spread it evenly basically, 10 in 1min"). A write refused for its size or a stale version spends none of them; `OTHER_SITES_MAX` (20) sites other than production per account (507 past it: the player deletes one).
- `ACCOUNTS_PER_DAY` (10) new accounts from one address, and `ASKS_PER_HOUR` (60) passkey options and sign-in codes from one address. The address is the last hop Traefik adds to `X-Forwarded-For`. All of these are counted in memory. An IPv6 address counts by its /64; empty counts and expired codes are pruned every 10 minutes, and challenges are held 10,000 at most.

## Cleanup (daily, `CLEAN_EVERY_MS`, and a minute after each start: a deploy restarts it more often than daily)

- A PR preview's saves go once GitHub's API (`GITHUB_REPO`, public, no token: 40 asked a run at most, under the 60 an hour it allows, the least lately asked first) says its PR is closed. A PR GitHub doesn't know (404) counts as closed. An empty `GITHUB_REPO` turns this part off, and `/saves/health` says `cleanup: false`.
- A commit build's saves go `COMMIT_KEEP_DAYS` (30) after their last write: GitHub doesn't know commit builds, and Dokci keeps one 30 days at most.
- Sessions unused for `SESSION_DAYS` go.

## Settings

None is required: each has its default in `settingsFrom`, or, unset, turns its part off, and `/saves/health` says so (the owner, 2026-11-10: "new env variables should be optional, if not set, the new func should be disabled"). A new setting must keep it so. The secrets are Google's: `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET` (the sign-in and the backups) and `DRIVE_REFRESH_TOKEN` (the backups), from Dokci's configuration (`LS_GOOGLE_CLIENT_ID`, `LS_GOOGLE_CLIENT_SECRET`, `LS_DRIVE_REFRESH_TOKEN`), never in the repo. Unset, there is no Sign in with Google (the game hides its buttons: the health's `google`) and no backups. `GOOGLE_REDIRECT_URI`, `GOOGLE_AUTH_URL`, `GOOGLE_TOKEN_URL` and `DRIVE_API` default to Google's own, and are set otherwise only by the tests.

## Storage

- Files on the `saves-data` volume at `/data`: `accounts/<id>.json` (passkeys' public keys and counters, sessions' digests, which sites have a save, their sizes and times) and `saves/<id>/<site>.json` (the parts, base64 of their gzip).
- Every file is written whole to a temporary name and renamed over the old, and each account's changes wait their turn (`withAccount`): a version's check and the write it allows are never split.
- Accounts are read into memory at a start; saves are read when asked for.
- Logs name an account by the first 6 letters of its id, and never hold a save's contents.
- Deleting an account removes its file and every save. The nightly backups keep it until they age out (14 days).

## Gotchas

- **The passkey library is pinned** (`@simplewebauthn/server` 14.0.3, and `tslib` by `overrides`): each version was at least two weeks old when taken. Its install scripts stay off (`--ignore-scripts`, in the image too). Under Node it logs Web Crypto's experimental warnings at its first use; they are harmless.
